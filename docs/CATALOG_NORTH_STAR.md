# Catalog North-Star — продуктовая рамка каталога У-Стройка

**Статус:** ориентир (north-star). Действует для всех итераций каталога — Timeweb MVP и финальной Cloudflare SSR.
**Дата:** 2026-06-29.

## 1. Что такое У-Стройка

У-Стройка — это **не лендинг с несколькими товарами, а SEO-движок товарного каталога стройматериалов**.
Главная ценность = органический трафик по тысячам товарных и категорийных запросов и удобный справочник по материалам (кровля, фасад, водосток, комплектующие).

Ориентир потока пользователя и бота:

```
категории → товары → фильтры → SEO-срезы → карточки → перелинковка → быстрые цены/наличие
```

## 2. Главные принципы (обязательны для любой итерации)

1. **HTML-first.** Товары, категории, хлебные крошки, H1, карточки, цена/наличие/характеристики
   должны присутствовать **в HTML при первой загрузке** (SSG или SSR), а не дорисовываться JS.
2. **JavaScript только улучшает интерактив** (фильтры на клиенте, слайдер цены, табы), но **не является
   основой каталога**. Отключённый JS не должен «прятать» товары от пользователя и бота.
3. **Не SPA-only каталог.** Никаких «пустых» HTML-каркасов, наполняемых только из JS/fetch.
4. **Не грузить большой JSON в браузер.** Снимок 20 МБ и сырьё 230k — никогда в client-бандл.
   Данные раздаются как HTML (страницы) и/или маленькими порциями.
5. **Не индексировать хаотичные query-фильтры.** Комбинации `?brand=&sort=&page=` → `noindex` +
   `canonical` на чистый URL подкатегории.
6. **SEO-срезы только через allowlist.** Индексируемые срезы (например «металлочерепица + бренд X»)
   создаются осознанно, по белому списку, а не автогенерацией всех комбинаций.
7. **SEO-чистые URL с ID в конце** (финальная архитектура) — см. §5.
8. **Карточка товара = справочник, а не пустая плитка** — см. §4.
9. **Timeweb MVP — временный быстрый запуск/staging.** Минимальный каталог (категории + витрина +
   demo-карточки). Не финал.
10. **Cloudflare SSR — финальная архитектура полного каталога** (230k, server-side фильтры, sitemap из
    БД). См. `CLOUDFLARE_SSR_ROADMAP.md`.

## 3. Каталог как модель данных

Каталог — это модель данных, а не набор страниц. Сущности (финальная архитектура, ориентир для D1):

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| `category` | дерево разделов/подразделов | id, slug, parent_id, title, description |
| `product` | товар | id, slug, category_id, brand_id, name, unit, images, description |
| `brand` | производитель | id, slug, title |
| `specification` | характеристика (тип) | id, key, label, unit |
| `specValue` | значение характеристики у товара | product_id, specification_id, value |
| `price` | цена | product_id, value, currency, source, updated_at |
| `stock` | наличие | product_id, status/qty, updated_at |

Цены/наличие — «быстрый» слой (live из источника + кэш), не вмешиваются в индексируемый HTML-каркас.

## 4. Карточка товара (минимум — справочник)

Карточка товара в HTML обязана содержать минимум:

- `H1` = название товара;
- фото (или честный placeholder);
- цена / наличие (наличие не выдумывать — если неизвестно, писать «Наличие уточняется»);
- артикул/код товара;
- характеристики (таблицаспецификаций);
- хлебные крошки (Главная → Каталог → Категория → Подкатегория → Товар);
- `Product` + (при реальной цене) `Offer` + `BreadcrumbList` JSON-LD;
- перелинковка: «вам может понадобиться» / назад в подкатегорию.

Запрещено: карточка-плитка без характеристик, без кода, без хлебных крошек.

## 5. URL и SEO

**Финальная архитектура — SEO-чистые URL с ID в конце:**

```
/category/<slug>-<id>/
/product/<slug>-<id>/
```

Причина: slug читаем для SEO и человека, `id` в конце даёт стабильную, неконфликтную адресацию
(переименование товара не ломает URL; ID — источник истины).

**Правила индексации:**

- `canonical` всегда на чистый URL **только под `https://y-stroika.ru`** (с дефисом);
- query-фильтры (`?brand=&sort=&page=`) → `noindex,follow` + `canonical` на подкатегорию;
- `sitemap` — только индексируемые URL (категории, подкатегории, карточки, allowlist-срезы),
  **никогда не весь сырой каталог хаотично**;
- SEO-срезы — по allowlist (осознанный список), не автогенерация всех комбинаций.

## 6. Migration path (текущие URL → финальные)

Текущие URL MVP **не считаются финальными**:

```
сейчас (MVP):   /catalog/<category>/<subcategory>/            (листинг)
                /catalog/<category>/<subcategory>/<code>/     (карточка, code = vendor)

финал (CF SSR): /category/<slug>-<id>/
                /product/<slug>-<id>/
```

План перехода (когда делается Cloudflare-каталог):

1. Ввести `id` как источник истины (product_id, category_id) в D1.
2. Сгенерировать новые URL `/<slug>-<id>/`.
3. На каждый старый `/catalog/...` URL поставить **301** на новый (карта редиректов; на Timeweb — `.htaccess`,
   на Cloudflare — правило/функция).
4. Обновить внутренние ссылки, `canonical`, `sitemap`, хлебные крошки на новые URL.
5. Снять старые URL из sitemap, оставить только 301.

До миграции допустимо жить на текущих `/catalog/...` URL — но новый код не должен закладывать
предположения, мешающие переходу на `/<slug>-<id>/`.

## 7. Категорийная страница (минимум)

- хлебные крошки + `H1`;
- счётчик товаров (когда есть полный каталог);
- список подкатегорий / связанные блоки;
- сетка товаров (в HTML);
- SEO-блок (текст категории);
- `CollectionPage` + `BreadcrumbList` JSON-LD.

## 8. Чего НЕ делать (анти-паттерны)

- SPA-only каталог; пустой HTML + JS-наполнение;
- большой JSON каталога в браузер;
- индексация всех query-комбинаций;
- автогенерация SEO-срезов без allowlist;
- карточка без характеристик/кода/хлебных крошек;
- выдуманное «В наличии» при неизвестном остатке;
- считать Timeweb MVP финальной архитектурой каталога.
